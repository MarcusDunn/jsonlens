# Requirement catalog for jsonlens.
#
# Format: id | type | owner | statement
#
#   id         The section number of RFC 9535 (see spec/rfc9535.txt), a slash, and a short name.
#              Rows that start with "lib/" are requirements of this library, not of the RFC.
#   type       requirement  The implementation must do this. A test must cover it.
#              option       The RFC permits a choice. The statement gives our decision. A test must cover it.
#              declined     The RFC permits it, but we do not do it. The statement gives the reason. No test.
#   owner      The Gradle project whose tests must cover the row, for example path-parser or patch.
#   statement  What the test must show.
#
# A test refers to a row with @Requirement("<id>"). The "check" task of each module fails if a
# test refers to an unknown id, or if a row that the module owns has no test.

# ---------------------------------------------------------------------------------------------
# Library requirements
# ---------------------------------------------------------------------------------------------
lib/core-dependencies               | requirement | path-core      | At runtime, the core module requires only java.base and the model module. JSpecify is a compile-time (static) requirement only.
lib/parser-dependencies             | requirement | path-parser    | At runtime, the parser module requires only java.base and the core module. JSpecify is a compile-time (static) requirement only.
lib/evaluator-dependencies          | requirement | path-evaluator | At runtime, the evaluator module requires only java.base and the core module. JSpecify is a compile-time (static) requirement only.
lib/core-exception-free             | requirement | path-core      | With non-null arguments, no public operation of the core module throws an exception.
lib/parser-exception-free           | requirement | path-parser    | With non-null arguments, the parser returns a value for all input. It does not throw an exception.
lib/evaluator-exception-free        | requirement | path-evaluator | With non-null arguments and a well-formed JsonModel, the evaluator returns a value for all queries and JSON values. It does not throw an exception.
lib/errors-as-values                | requirement | model     | Operations that can fail return a sealed Result of a value or an error record.
lib/model-zero-copy                 | requirement | model     | A JsonModel gives access to the nodes of the caller's own JSON representation. It does not copy or convert them.
lib/absence-as-values               | requirement | model     | A value that can be absent is a sealed Maybe (Some or None), not null and not Optional.
lib/model-explicit-absence           | requirement | model     | A JsonModel reports a missing member or element as Maybe.None. JSON null is a present node of kind NULL.
lib/model-defaults                   | requirement | model     | A JsonModel implements six methods: kind, arrayLength, element, memberCursor, stringValue, and numberValue. The other methods have defaults that use the six; memberCount, member, members, and hasDuplicate walk the member cursor.
lib/model-equal-nodes                | requirement | model     | A JsonModel can make a new node object for each read of a value. Two reads of the same value give equal nodes with the same hash code. jsonlens does not compare nodes by reference.
lib/model-no-null-arguments         | requirement | path-evaluator | The evaluator never calls a JsonModel method with a null argument.
lib/model-kind-preconditions        | requirement | path-evaluator | The evaluator calls a kind-specific JsonModel method only for a node of that kind.
lib/core-null-marked                | requirement | path-core      | All exported packages of the core module are @NullMarked (JSpecify). NullAway checks them at compile time.
lib/model-dependencies              | requirement | model     | At runtime, the model module requires only java.base. JSpecify is a compile-time (static) requirement only.
lib/model-null-marked               | requirement | model     | All exported packages of the model module are @NullMarked (JSpecify). NullAway checks them at compile time.
lib/parser-null-marked              | requirement | path-parser    | All exported packages of the parser module are @NullMarked (JSpecify). NullAway checks them at compile time.
lib/evaluator-null-marked           | requirement | path-evaluator | All exported packages of the evaluator module are @NullMarked (JSpecify). NullAway checks them at compile time.
lib/no-json-types-in-api            | requirement | path-core      | The public API has no JSON value types. JSON values are always of the caller's type parameter N.
lib/model-number-representation     | requirement | model     | The model chooses the representation of numbers. Each JsonNumber gives its exact value as a JsonDecimal, with no limit on the exponent; JsonNumber.of(...) makes the common cases.
lib/model-number-comparison         | requirement | model     | The model compares numbers with JsonModel.compareNumbers. The default compares the exact values. Each implementation gives the same sign as the comparison of the exact values.
lib/model-string-representation     | requirement | model     | The model chooses the representation of strings. A JsonString gives its Unicode scalar values in order; JsonString.of(String) makes the common case without a copy.
lib/model-member-names              | requirement | path-core      | Member names are JsonStrings in the representation of the model. Equality and hash codes of properties and Normalized Paths use the scalar values, so names in different representations are equal.
lib/model-factory                   | requirement | model     | A JsonFactory builds nodes of the model. The read methods give the exact value of each built node again.
lib/model-equality-and-copy          | requirement | model     | JsonModel.equal compares two values as RFC 9535 and RFC 6902 define equality. JsonFactory.copyOf builds a deep copy of a value of any model. Neither uses recursion.
lib/model-editor                    | requirement | model     | A JsonEditor changes objects and arrays in place. Each method returns the value that it replaced or removed, so that a caller can reverse the change.

# 1. Introduction
# ---------------------------------------------------------------------------------------------
1.1/unicode-scalar-values      | requirement | path-parser    | A query is a sequence of Unicode scalar values. The parser rejects a query string that contains an unpaired surrogate.
1.1/children                   | requirement | path-evaluator | The children of an array are its elements. The children of an object are its member values. A primitive value has no children.
1.1/descendants                | requirement | path-evaluator | The descendants of a node are its children, the children of its children, and so on.
1.1.1/member-names-not-nodes   | requirement | path-evaluator | Only member values are nodes. A query never selects a member name.
1.3/json-value-kinds           | requirement | model     | A JsonModel classifies each node as one of the seven JSON kinds: object, array, number, string, true, false, null.
1.3/duplicate-names            | option      | path-evaluator | The RFC does not define behavior for duplicate member names. Decision: the JsonModel decides which member value member() returns and which members members() returns.
1.3/non-scalar-strings         | option      | path-core      | The RFC does not define behavior for strings that are not sequences of Unicode scalar values. Decision: a normalized path writes an unpaired surrogate in a member name without change.

# 2.1 Overview

2.1/well-formed                | requirement | path-parser    | The parser rejects a query that does not agree with the ABNF grammar.
2.1/ijson-integer-range        | requirement | path-parser    | The parser rejects an index, slice start, slice end, or slice step outside [-(2^53)+1, (2^53)-1].

2.1/validity-independent-of-value | requirement | path-parser | The parser checks well-formedness and validity without a JSON value.
2.1/no-validity-errors-at-evaluation | requirement | path-evaluator | The evaluator does not report well-formedness or validity errors for a parsed query.
2.1/overflow-indication        | requirement | path-evaluator | When a JSON value is too large to process correctly, the evaluator gives an indication of overflow. It does not give a wrong result.
2.1/diagnostics                | declined    | path-evaluator | The RFC suggests diagnostics for empty results. We do not supply them in the first version.

# 2.3.5 Filter selector
2.3.5/children                 | requirement | path-evaluator | A filter selector evaluates its logical expression once for each child. The child is the current node.
2.3.5.1/syntax                 | requirement | path-parser    | A filter selector is "?" followed by optional blank space and a logical expression.
2.3.5.1/current-node           | requirement | path-evaluator | "@" refers to the current node of the filter selector that directly encloses it.
2.3.5.1/evaluation-order       | option      | path-evaluator | The RFC permits short-circuit or full evaluation of && and ||. Decision: short-circuit evaluation.
2.3.5.1/logical-operators      | requirement | path-evaluator | ||, &&, and ! have the semantics of Boolean algebra.
2.3.5.1/precedence             | requirement | path-parser    | Operator precedence is as in Table 10: grouping and functions, then !, then relations, then &&, then ||.
2.3.5.1/parentheses            | requirement | path-parser    | Parentheses can group a logical expression. A parenthesized expression can have a "!" before it.
2.3.5.1/test-expr              | requirement | path-parser    | A test expression is an optional "!" followed by a filter query or a function expression. The parser rejects a literal as a test expression.
2.3.5.1/filter-query           | requirement | path-parser    | A filter query is a relative query (starts with "@") or an absolute query (starts with "$").
2.3.5.1/comparable             | requirement | path-parser    | Each side of a comparison is a literal, a singular query, or a function expression. The parser rejects a non-singular query in a comparison.
2.3.5.1/singular-query         | requirement | path-parser    | A singular query has only name segments and index segments, each with one selector.
2.3.5.1/comparison-operators   | requirement | path-parser    | The comparison operators are == != <= >= < and >.
2.3.5.1/literals               | requirement | path-parser    | A literal is a number, a string, true, false, or null. true, false, and null are lowercase only.
2.3.5.1/number-syntax          | requirement | path-parser    | A number literal is (int / "-0") [frac] [exp]. The exponent marker can be "e" or "E".
2.3.5.2/structured-only        | requirement | path-evaluator | A filter selector selects nothing from a primitive value.
2.3.5.2/array-order            | requirement | path-evaluator | A filter selector selects array elements in array order.
2.3.5.2/object-order           | option      | path-evaluator | The RFC does not specify the order of object children. Decision: the order of JsonModel.members().
2.3.5.2.1/existence            | requirement | path-evaluator | A query used as a test is true if it selects at least one node, else false.
2.3.5.2.2/empty-equality       | requirement | path-evaluator | When one side of == is an empty nodelist or Nothing, the result is true only if the other side is also empty or Nothing.
2.3.5.2.2/empty-less-than      | requirement | path-evaluator | When one side of < is an empty nodelist or Nothing, the result is false.
2.3.5.2.2/number-equality      | requirement | path-evaluator | Numbers in the I-JSON range are equal if they are mathematically equal, for example 1 and 1.0.
2.3.5.2.2/number-ordering      | requirement | path-evaluator | Numbers in the I-JSON range compare in their mathematical order.
2.3.5.2.2/non-interoperable-numbers | option | path-evaluator | Equality and order of numbers outside I-JSON are implementation-specific. Decision: compare the exact values of the JsonNumbers that the model gives, as for I-JSON numbers. Each JSON number has an exact value, so each comparison is exact, also with a very large exponent.
2.3.5.2.2/primitive-equality   | requirement | path-evaluator | Strings, true, false, and null are equal only to the same primitive value.
2.3.5.2.2/array-equality       | requirement | path-evaluator | Arrays are equal if they have the same length and the elements at each position are equal.
2.3.5.2.2/object-equality      | requirement | path-evaluator | Objects are equal if they have the same names and the values for each name are equal.
2.3.5.2.2/kind-mismatch        | requirement | path-evaluator | Values of different kinds are never equal. For example, 1 == "1" and null == false are false.
2.3.5.2.2/string-ordering      | requirement | path-evaluator | Strings compare by Unicode scalar values, not by UTF-16 code units.
2.3.5.2.2/less-than-kinds      | requirement | path-evaluator | < is false unless both sides are numbers or both sides are strings.
2.3.5.2.2/derived-operators    | requirement | path-evaluator | !=, <=, >, and >= are defined from == and < as the RFC specifies.

# RFC 9485 (I-Regexp), for match() and search()
# ---------------------------------------------------------------------------------------------
rfc9485-3/checking             | requirement | path-evaluator | The I-Regexp implementation is checking. A regexp that does not agree with RFC 9485, Figure 1 is not valid, including "[^]", a reversed range, and a reversed quantifier.
rfc9485-3/unicode              | requirement | path-evaluator | The I-Regexp implementation supports all Unicode scalar values, and the category escapes \p{..} and \P{..}.
rfc9485-4/xsd-semantics        | requirement | path-evaluator | The I-Regexp implementation has XSD semantics: for example, "." does not match "\n" or "\r", and match() requires a match of the complete string.
rfc9485-4/anchors              | option      | path-evaluator | In XSD, "^" and "$" are ordinary characters, but the JSONPath Compliance Test Suite and the mappings of RFC 9485, Section 5 make them anchors. Decision: outside a character class, "^" matches only at the start and "$" only at the end of the input.
rfc9485-8/range-quantifiers    | option      | path-evaluator | RFC 9485 lets an implementation limit range quantifiers. Decision: a regexp with a program larger than the limit, or with more than 256 nested groups, gives the overflow indication RegexTooComplex.

# RFC 6901: JSON Pointer (spec/rfc6901.txt). The pointer module owns these rows.
# ---------------------------------------------------------------------------------------------
rfc6901-3/syntax               | requirement | pointer   | A pointer is empty, or "/" followed by reference tokens separated by "/". Text that is not empty and does not start with "/" is an error.
rfc6901-3/escaping             | requirement | pointer   | "~0" encodes "~" and "~1" encodes "/" in a token. A "~" that is not followed by "0" or "1" is an error. Writing a pointer escapes "~" and "/".
rfc6901-3/characters           | requirement | pointer   | A pointer is a string of characters. A token can hold any character other than an unescaped "/" or "~", for example non-ASCII characters and U+0000 (also Section 8).
rfc6901-4/decode-order         | requirement | pointer   | Decoding gives "~1" for "~01": "~1" becomes "/" and then "~0" becomes "~", never the reverse.
rfc6901-4/object-member        | requirement | pointer   | For an object, a token selects the member with the same Unicode code points. There is no Unicode normalization.
rfc6901-4/duplicate-names      | requirement | pointer   | If the selected member name is not unique in the object, the evaluation fails.
rfc6901-4/array-index          | requirement | pointer   | For an array, a token is "0" or digits without a leading zero, and selects the element at that zero-based index. Other tokens are errors.
rfc6901-4/dash                 | requirement | pointer   | The token "-" references the nonexistent element after the last element, so the evaluation fails. An application of JSON Pointer (JSON Patch) defines its use.
rfc6901-4/unresolved           | requirement | pointer   | The evaluation fails if a token does not resolve to a value: a missing member, an index outside the array, or a token after a value that is not an object or an array.
rfc6901-5/json-string          | requirement | pointer   | The pointers of the example in Section 5 select the documented values.
rfc6901-6/uri-fragment         | requirement | pointer   | The URI fragment form is "#" and the UTF-8 bytes of the pointer, with percent-encoding for each byte that a fragment does not permit. The fragments of Section 6 select the documented values.
rfc6901-7/errors               | requirement | pointer   | Each error condition is a PointerError value that tells the cause. The library does not throw.
lib/pointer-model-agnostic     | requirement | pointer   | A pointer resolves against the values of any JsonModel (Jackson, kotlinx, mapped, Java collections), and gives the caller's own node without a copy.
lib/pointer-dependencies       | requirement | pointer   | At runtime, the pointer module requires only java.base and the model module.
lib/pointer-null-marked        | requirement | pointer   | All exported packages of the pointer module are @NullMarked (JSpecify).

# RFC 6902: JSON Patch (spec/rfc6902.txt). The patch module owns these rows.
# ---------------------------------------------------------------------------------------------
rfc6902-3/document             | requirement | patch     | A patch document is an array of operation objects. Another document is an error.
rfc6902-3/sequential           | requirement | patch     | The operations apply in order. Each operation applies to the result of the previous operation.
rfc6902-4/op-member            | requirement | patch     | Each operation has exactly one "op" member, a string with one of the six operation names. Other values, a missing "op", and two "op" members are errors.
rfc6902-4/path-member          | requirement | patch     | Each operation has exactly one "path" member, a string with a JSON Pointer.
rfc6902-4/operation-members    | requirement | patch     | add, replace, and test need a "value" member; move and copy need a "from" member with a JSON Pointer.
rfc6902-4/ignore-members       | requirement | patch     | Members that an operation does not define are ignored.
rfc6902-4.1/add                | requirement | patch     | add replaces the whole document, adds or replaces an object member, or inserts an array element and shifts the next elements. "-" appends.
rfc6902-4.1/add-errors         | requirement | patch     | For add, the parent of the target location must exist and be a container, and an array index must not be greater than the length.
rfc6902-4.2/remove             | requirement | patch     | remove removes the value at the target location, which must exist. Array elements after it shift to the left.
rfc6902-4.2/remove-root        | option      | patch     | RFC 6902 does not define a remove of the whole document. Decision: it is the error RootRemoved, because the document cannot be absent.
rfc6902-4.3/replace            | requirement | patch     | replace replaces the value at the target location, which must exist.
rfc6902-4.4/move               | requirement | patch     | move removes the value at "from" and adds it at the target location, which is evaluated after the removal. A move to the same location has no effect, but "from" must exist.
rfc6902-4.4/move-errors        | requirement | patch     | The "from" location of move must exist, and must not be a proper prefix of the target location.
rfc6902-4.5/copy               | requirement | patch     | copy adds a copy of the value at "from", which must exist, at the target location.
rfc6902-4.6/test               | requirement | patch     | test succeeds only if the values have the same JSON type and are equal: strings by code points, numbers by value, arrays in order, objects without order, and literals.
rfc6902-5/atomic               | requirement | patch     | If an operation fails, the patch is not successful and the document has its original value again (the HTTP PATCH method is atomic). Only the order of members in an object can differ, because it is not significant (RFC 8259, Section 4).
rfc6902-5/errors               | requirement | patch     | Each error is a PatchError value with the index of its operation. The library does not throw.
rfc6902-6/media-type           | declined    | patch     | The media type application/json-patch+json is for transport. The library does not transport patch documents.
lib/patch-test-suite           | requirement | patch     | Each enabled record of the JSON Patch test suite gives its expected result or an error, on the Jackson and Java collections models, with the patch document in Jackson, kotlinx, and mapped.
lib/patch-model-agnostic       | requirement | patch     | A patch document can be in any JsonModel, and a target in any model that is also a JsonFactory and a JsonEditor.
lib/patch-minimal-copies       | requirement | patch     | move and test build no node. add and replace copy their value once. copy makes one deep copy. remove builds no node.
lib/patch-copy                 | requirement | patch     | applyToCopy applies a patch with only a JsonModel and a JsonFactory (for example kotlinx). The document never changes. Each change builds only the containers on its path; all other nodes are shared, and copy shares its source.
lib/patch-dependencies         | requirement | patch     | At runtime, the patch module requires only java.base, the model module, and the pointer module.
lib/patch-null-marked          | requirement | patch     | All exported packages of the patch module are @NullMarked (JSpecify).
